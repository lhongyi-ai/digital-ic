## Tool semantics and explicit limitations

Verilator counts control flow, signal changes, and Boolean expressions separately. This installed version actually outputs `line`, `branch`, `toggle`, and `expr` records. Branch coverage refers to conditional branch points generated by this tool; expression coverage is neither a full truth table nor an MC/DC proof. See [Verilator coverage analysis](https://verilator.org/guide/latest/simulating.html#coverage-analysis).

This version supports `--coverage-fsm` and `--coverage-user`, but this RTL generated **no automatic FSM state/arc points and no user-defined HDL cover points**. These categories are therefore N/A, neither a 0% functional failure nor 100% functional coverage. Six-phase reset tests and the four test names do not replace a complete FSM transition matrix, `cover property`, or covergroup. Executed assertions do not prove every condition combination or the entire state space.

**The toggle denominator has tool-default omissions.** No coverage-off directive, waiver, or report filter was added, but Verilator's default width/local-variable rules remain in effect. The actual point list shows:

- raw0, raw1, and windowed RAM are excluded from toggle counts in every configuration.
- With BANDS=1, frequency_bins, real_part, and imag_part each have 512 rising/falling-direction counter points. With BANDS=3, these arrays exceed the default 256-bit width limit and generate no toggle points.
- ROM data, feature shifts, biases, and other fixed parameters should not change continuously within one simulation, yet some counter points may remain. Startup initialization and reset transitions count; counters were not cleared before reset release.

These rules change denominators, so percentages cannot establish that BANDS=3 or LANES=4 is more reliable. The table only reports counts for the specified tool version, parameters, and tests. The official documentation above also describes default width omissions and startup transitions; this run additionally inspected actual `.dat` records point by point.

## Uncovered items and proposed handling

The explanations below interpret the raw counts; **no points were removed from any denominator**.

| Location | Actual gap/reason | Reasonable next step |
| --- | --- | --- |
| Core line 279 | A malformed frame with `in_last` on its first beat was not tested | Add a one-sample malformed frame and check the error count and subsequent normal-frame recovery |
| Core lines 282–283 | Missing last followed by a changed frame ID was tested; continued same-ID draining until a late last was not | Add continued drain, termination, and next-frame recovery; verify no stale output |
| Upper frame-ID bits | Existing IDs are small, leaving some high-bit copying and ID wraparound unstimulated | Add IDs near `0xffffffff` and check outputs |
| Core line 424 | No internal fault injection exercised default recovery from an illegal state | Design illegal-state injection separately from normal-input cases; reset tests are not a complete FSM proof |
| Core line 368 | Frozen-model feature shifts do not exceed 33 | The independent boundary profile hit this path; retain its verification-only label |
| Core lines 144, 156–175, 179–193 | Some general arithmetic guard branches were not triggered by complete input frames; `power_quant` is not the current serial-quantization datapath | Direct-function boundary evidence exists; derive ranges separately if end-to-end reachability must be closed, without inflating core coverage through direct calls |
| ROM lines 33–34 and some LANES/BANDS branches | HANN, LANES, and BANDS are fixed instance parameters; the opposite branch cannot execute in that instance | Retain separate reports for multiple configurations; a constant cannot take two values simultaneously |
| Core line 401 | Legal inputs for the frozen NN model did not trigger int32 overflow | Report numeric bounds from actual weights/biases; use a separate scenario for corrupted models |
| Assertion failure conditions for parameter/runtime invariants | Correct normal execution does not take error outcomes | Retain assertions and unhit points; do not break invariants merely to obtain full coverage |

NN bounds use `sum(abs(weight_row))*127 + abs(bias)`. Single-bin layer bounds are 79,152 and 113,999; neighbor-bin bounds are 70,515 and 88,778. All are far below INT32_MAX=2,147,483,647. These bounds for the specific models explain the unhit overflow branch; they do not establish safety for all possible weights or corrupted ROMs.

## Reproduction and inspection

Run from the project root. All new outputs go to `build/rtl_coverage`; no board is required:

```bash
.venv/bin/python scripts/run_core_coverage.py
```

Existing simulation outputs can be recollected without rerunning HDL. The script verifies source, model, and tool versions against the run manifest:

```bash
.venv/bin/python scripts/run_core_coverage.py --collect-only
```

Each `l*_b*/coverage` subdirectory retains raw merged data `merged.dat`, LCOV `coverage.info`, per-source annotations in `annotated/`, unhit points in `uncovered_points.json`, original official-tool output, and `summary.json`. LCOV and annotated files are views generated by the official [verilator_coverage tool](https://verilator.org/guide/latest/exe_verilator_coverage.html). Confirm that every test in the corresponding XML passed before interpreting coverage; the script already checks failures, errors, skips, and empty test sets.

The new `--coverage` and `--build-dir` options in `scripts/build_core.py` are optional; default behavior remains unchanged. Standalone coverage use should specify a separate build directory. Coverage is connected only to cocotb core/arithmetic regressions. Native fixed-rate runs, synthesis, and place-and-route commands without counter export are not labeled coverage runs.

These are RTL simulation results and do not include physical FPGA timing, USB, sensors, or actual power measurements.
